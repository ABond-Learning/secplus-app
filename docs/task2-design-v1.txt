1. EXECUTIVE SUMMARY
═══════════════════════════════════════════════════════════════════════════

Task 2 collapses 6 quiz sub-modes (Standard / New / Scenario / Spaced /
Weak / Matching) and the per-tab Cram into 4 mode-cards (Quiz /
Flashcards / Review / Drill Wrong) under a unified Study tab, with a
Customise drawer for filters and saved presets for recall. User
benefit: every study intent the old modes captured is reachable from
one place, with new compositions (e.g., "scenarios from D4 only,
prefer unseen, 30 questions") that the old hardcoded modes couldn't
express. Technical risk centers on cross-device migration ordering
(NOT on SM-2 key restructuring — the SM-2 keys are mode-agnostic and
stay as-is). The genuinely hard part is that adding "cram-" to
TRACKED_PREFIXES creates a transition window where old-version
devices can wipe new-version devices' cram progress unless we deploy
sync-engine prefix changes BEFORE any cram-prefixed keys exist
anywhere. This drives a "hygiene-first" decomposition with a
mandatory pre-batch (Sub-batch 0) before the feature work. Total
estimated scope: 6 sub-batches across 4-5 sessions. Sub-batches 0-2
are low-risk; sub-batches 3-4 carry medium risk because of sync
behavior; sub-batch 5 is cleanup.

────────────────────────────────────────────────────────────────────────
3.1. The 4 modes
────────────────────────────────────────────────────────────────────────

  Quiz       | Active study session: stem → answer → check → SM-2
             | rate. The "throw me questions and grade me" mode.
             | Replaces today's standard, scenario, new, drill.
             | User flow: pick filters → start → answer 5-50 questions
             | → see results → optional drill-wrong follow-up.

  Flashcards | Term/concept recall via card-flip UI. Front shows term
             | (or stem); back shows definition (or full answer + exp).
             | Optional rating panel after flip for SM-2 progress.
             | Replaces today's cram, plus matching as a sub-format.
             | User flow: pick filters → start → flip cards → optional
             | rate → next card.

  Review     | Spaced-repetition queue. Items where nextDue <= today,
             | optionally including never-seen items. Ordered by
             | overdue-ness (most-overdue first).
             | Replaces today's spaced.
             | User flow: pick filters → start → drill until queue
             | empty.

  Drill Wrong| Targeted weakness practice. Items below an accuracy
             | threshold OR recently-missed (last N sessions).
             | Replaces today's weak + post-exam drill-handoff.
             | User flow: pick threshold → start → drill weak items.

────────────────────────────────────────────────────────────────────────
3.2. The Customise drawer
────────────────────────────────────────────────────────────────────────

A side drawer on the Study tab, attached to whichever mode is
currently selected. Filter controls compose with AND semantics
(e.g., "D4 + scenarios + below-70%-accuracy" = items satisfying all
three). Mode-specific defaults pre-fill (e.g., Drill Wrong's accuracy
slider defaults to 70%; Review's dueOnly defaults to true).

Filter / scope:
  - Domain checkboxes (D1-D5), default checked, exam-weighted info.
  - Sub-objective filter (shown when one domain selected).
  - Specific-videos filter (searchable list).
  - Watched-videos-only toggle (default ON).

Format / type:
  - questionTypes: { mc, scen, match, cram } — checkboxes.
  - Mode-specific defaults: Quiz {mc, scen}; Flashcards {cram};
    Review {mc, scen}; Drill Wrong {mc, scen}.

Length / pacing:
  - Length slider (5-50 for Quiz, 10-100 for Flashcards, "all" for
    Review/Drill).
  - activeRecall toggle.
  - revealOptions toggle.

Quality / SM-2 filter:
  - preferUnseen toggle (subsumes today's New mode).
  - belowAccuracy threshold slider (subsumes today's Weak mode).
  - dueOnly toggle (Review default ON; subsumes Spaced).

Pool preview shows live count: "Drawing N items from M videos"
updates as filters change.

────────────────────────────────────────────────────────────────────────
3.3. Saved presets
────────────────────────────────────────────────────────────────────────

A preset is a named drawer configuration plus mode selection.

Concrete shape:

  {
    "id": "01HXY8K4...",          // ULID/UUID
    "name": "D4 weak spots",
    "mode": "drill",              // quiz | flashcards | review | drill
    "filters": {
      "domains": ["4"],
      "subObjectives": [],
      "videoIds": [],
      "watchedOnly": true,
      "questionTypes": ["mc", "scen"],
      "preferUnseen": false,
      "belowAccuracy": 0.70,
      "dueOnly": false,
      "length": 25,
      "activeRecall": false,
      "revealOptions": true
    },
    "createdAt": "2026-05-02T12:34:56Z",
    "lastUsedAt": "2026-05-03T09:21:11Z"
  }

Storage: a single localStorage key holding an array of presets.
Storage shape choice (Q-C below): single-array vs per-preset-key.
Recommendation: single-array under `secplus-v4-presets` for the
v1 implementation. Last-write-wins on the array; race window is
small (~5s sync debounce + user creating multiple presets in that
window).

Synced via TRACKED_PREFIXES "secplus-" automatically. No engine
changes needed for presets alone.

User management UI: preset list in drawer header, "Save current as
preset" button, per-preset Apply/Rename/Delete actions.

4.4. SPACED mode → Review
────────────────────────────────────────────────────────────────────────

INTENT 1: "What's due for review today?"
  drawer_config = {
    mode: "review",
    filters: { dueOnly: true, watchedOnly: true,
               questionTypes: ["mc","scen"] }
  }
  ✓ Direct mapping. Pool size is "all due" (no length slice).

INTENT 2: "Spaced session including unseen items" (today's spaced
           ALREADY does this — !rec || rec.nextDue <= today)
  drawer_config = {
    mode: "review",
    filters: { dueOnly: false, ... } // dueOnly off so unseen items
                                     // also surface
  }
  OR
  drawer_config = {
    mode: "review",
    filters: { dueOnly: true, preferUnseen: true, ... }
  }
  ⚠ AMBIGUOUS: today's spaced mode mixes due AND unseen by default.
    The drawer has TWO toggles (dueOnly, preferUnseen) that interact
    in ways that need explicit definition:
      - dueOnly=true, preferUnseen=false  → only items with SM-2
        records that are due today
      - dueOnly=true, preferUnseen=true   → only items where the
        record is due AND the item is unseen (impossible — unseen
        items have no record)
      - dueOnly=false, preferUnseen=false → all watched-video items
        (basically Quiz with no filter)
      - dueOnly=false, preferUnseen=true  → unseen-only (=== New mode)
    Today's spaced is NONE of these — it's "items where !rec OR
    rec.nextDue<=today" = "due-or-new."

  Resolutions:
    (a) Accept loss: ditch the "due OR new" combined behavior.
        Force user to pick due-only or unseen-only. NEUTRAL: today's
        spaced behavior is convenient but not essential.
    (b) Extend drawer: add a third toggle "includeUnseen" that, when
        on, includes items without SM-2 records alongside the
        due-filtered items. EXPLICIT.
    (c) Re-evaluate: rename Review mode to "Daily Practice" and
        define its semantics as "due OR unseen" by default. Implicit
        behavior; presets can override.
  Recommendation flagged for Aiden; my pick is (b) — explicit
  composition is cleaner than implicit "due OR unseen" defaulting.

INTENT 3: "Spaced restricted to my weak items" (i.e., compose with
           weak-mode threshold)
  drawer_config = {
    mode: "review",
    filters: { dueOnly: true, belowAccuracy: 0.70, ... }
  }
  ✓ Drawer composition handles this. Today, you cannot do this in
    one session — today's modes are mutually exclusive. Net gain.

────────────────────────────────────────────────────────────────────────
4.5. WEAK mode → Drill Wrong
────────────────────────────────────────────────────────────────────────

INTENT 1: "Drill items from my below-70% videos"
  drawer_config = {
    mode: "drill",
    filters: { belowAccuracy: 0.70, watchedOnly: true,
               questionTypes: ["mc","scen"] }
  }
  ⚠ SEMANTIC SHIFT: today's weak mode operates at the VIDEO level
    (videos whose AVERAGE accuracy is below 70%, then ALL questions
    from those videos enter the pool). The new "belowAccuracy"
    drawer filter could operate at:
      (a) VIDEO level (today's behavior — preserves identity)
      (b) PER-QUESTION level (filter to individual questions whose
          own accuracy is below threshold; needs per-question
          accuracy tracking that we have via SM-2.correct/total)
      (c) BOTH levels (drawer toggle: "accuracy scope: video |
          question")
    Today's per-video logic surfaces "videos I'm struggling with"
    holistically; per-question would surface "specific items I
    repeatedly miss" more granularly. Both are useful pedagogically.

  Resolutions:
    (a) Accept video-level only — preserves today's behavior, no new
        capability.
    (b) Accept per-question only — more granular, loses "this whole
        video is shaky" view.
    (c) Both — drawer toggle. Adds complexity but neither is lost.

  Recommendation: (c) with default = per-question. Today's video-
  level was a workaround for the absence of granular SM-2 tracking
  in the original simple-quiz design; we now have per-question SM-2
  records, so per-question filtering is the more powerful default.
  Video-level can be exposed as an advanced toggle.

INTENT 2: "Drill the items from my last exam I got wrong" (post-exam
           handoff)
  This is NOT a Customise-drawer flow. The Exam tab's "Drill N Wrong"
  button programmatically loads a specific question set into Quiz
  mode (today: setupMode="drill"). In the new world, this becomes:
  "Open Drill Wrong mode with a preloaded question list, bypassing
  the drawer." A separate code path.
  ✓ Preserved as a special invocation. Drawer still expressible
    after the drill ends (user can save the explicit list as a
    preset? — probably not; the question list isn't a filter
    expression).

────────────────────────────────────────────────────────────────────────
4.6. MATCHING mode → ??? (HARD CASE)
────────────────────────────────────────────────────────────────────────

Today's matching mode has a DISTINCT running-quiz UI:
MatchingQuestion component, dropdown selects per prompt, "Check
Answers" button, partial-credit per pair, no rating panel (binary
correct/wrong via recordResult, not recordRating).

INTENT: "Practice term-to-definition matching for video X"

Where does this fit in the new world?

OPTION 1: Quiz mode with questionTypes=["match"] filter.
  - Pro: matching exercises are "questions" in the same study session.
  - Con: the UI flow is jarringly different from MC (dropdown vs
    radio-button, Check Answers vs check-and-rate). Mid-session
    switching between MC and matching cards is disruptive.

OPTION 2: Flashcards mode with questionTypes=["match"] filter.
  - Pro: matching is conceptually "flip-and-recall"-style — you see
    prompts and have to associate them with answers, similar to
    flashcards.
  - Con: matching's UI is MORE structured than flashcards (multi-
    pair structure, partial credit, all-at-once Check), not really
    flip-style.

OPTION 3: Matching as its own first-class fifth mode.
  - Pro: preserves today's distinct UI without trying to shoehorn it
    elsewhere. Clean.
  - Con: 5 modes instead of 4 — undermines the consolidation
    narrative.

OPTION 4: Matching as a sub-mode under Flashcards, with a separate
           "Matching" tab inside the Flashcards mode picker.
  - Pro: Flashcards becomes "term-recall" surface; matching is one
    of two sub-formats (single-card flashcards + multi-pair matching
    grids).
  - Con: nested mode picker adds a layer.

OPTION 5: Embed matching INSIDE Quiz mode but render
           MatchingQuestion as a "panel-style" card that doesn't
           interleave with MC.
  - Pro: 4-mode story preserved.
  - Con: pool-build still needs to know whether to interleave or
    cluster matching items. Complexity moves from UI to pool logic.

⚠ RESOLUTION REQUIRED — Aiden's call.
Recommendation: OPTION 1 (Quiz mode with type filter) BUT with
question-type clustering: matching items render as a contiguous
block at the start or end of the session, not interleaved. This
keeps the 4-mode story while preserving matching's distinct flow.
Alternative: OPTION 3 — accept 5 modes. Cleaner conceptually if
4-mode framing is flexible.

POSSIBLE SHAPE-ADDITIVE on secplus-v4:
  If we add a `lastUsedPresetId` field to the umbrella store (so the
  Study tab opens with the most-recent preset pre-applied), that's an
  ADDITIVE shape change. migrateStore's spread (`{ ...DEFAULT_STORE,
  ...data, version: SCHEMA_VERSION }`) preserves unknown fields, so
  V_old reading a V_new store doesn't lose this field. However, if
  we rely on this field's presence for behavior, we need to handle
  V_old → V_new transition (V_new reads a store that lacks the
  field; default to first preset or "no preset selected").

  Recommendation: AVOID adding fields to secplus-v4 in Task 2 unless
  necessary. Use new top-level keys instead. Keeps the umbrella
  store stable.

(Only NEW keys exist post-Task-2; the migration story is therefore

────────────────────────────────────────────────────────────────────────
5.3. schemaVersion bump decision
────────────────────────────────────────────────────────────────────────

There are TWO version numbers; analyze both.

(A) STORE_KEY internal version (currently 2):
    Bumping this triggers migrateStore's version-guarded code path.
    Should we bump?
      - If we add `lastUsedPresetId` (or similar) to umbrella store:
        NO bump needed; spread preserves unknown fields.
      - If we change the SHAPE of an existing field (e.g., history[]
        items gain new fields): NO bump needed; additive changes
        are safe because of the spread.
      - If we REMOVE a field or change its semantics: BUMP — but
        Task 2 doesn't require this.
    DECISION: NO bump. Stay at version 2. Confirms PLAN.md's
    expectation.

(B) PAYLOAD_SCHEMA_VERSION (currently 1):
    Bumping this changes the Gist wrapper shape. The wrapper is
    `{ schemaVersion, deviceId, lastWriteAt, entries: { ... } }`.
    Adding new keys to `entries` does NOT change the wrapper shape.
    DECISION: NO bump. Stay at PAYLOAD_SCHEMA_VERSION = 1.
    Confirms PLAN.md's expectation.

NEITHER VERSION NEEDS BUMPING. The "migration" is purely additive:
new keys, new prefixes, new LOCAL_ONLY entries. All of which old
code naturally either ignores (new keys) or fails to filter (new
prefixes — see 5.4 below for the data-loss scenario this enables).

────────────────────────────────────────────────────────────────────────
5.4. CROSS-DEVICE MIGRATION ORDERING (DEDICATED — the genuinely
     tricky part)
────────────────────────────────────────────────────────────────────────

Setup: Aiden has 3 devices. They sync via Gist. Each device runs
the bundled JS shipped at the time it last loaded the page. Unless
the user actively reloads, a device may run V_old after V_new ships.

The transition window is "between the moment V_new is deployed and
the moment all 3 devices have loaded V_new." During this window,
some devices run V_old and some run V_new simultaneously.

Walk-through per migration class:

────────────
(a) RENAMED keys
────────────

Task 2 has NO renamed keys (per 5.1). This scenario doesn't apply.

────────────
(b) SHAPE-CHANGED keys
────────────

Task 2 has NO shape-changed keys (per 5.1; possibly additive on
secplus-v4 but not changed semantics).

For ADDITIVE-ONLY shape changes (e.g., adding `lastUsedPresetId`
to secplus-v4):

  Step 1: V_new on Device A writes secplus-v4 with lastUsedPresetId
          field added.
  Step 2: V_new pushes to Gist. Gist's secplus-v4 entry now has the
          new field embedded in its JSON value.
  Step 3: V_old on Device B pulls. V_old's loadStore reads the
          payload. migrateStore does
          `{ ...DEFAULT_STORE, ...data, version: SCHEMA_VERSION }`.
          The lastUsedPresetId field passes through the spread
          UNTOUCHED (DEFAULT_STORE doesn't have it; data does).
          V_old then writes back via saveStore — the field is
          preserved across the round-trip.
  Step 4: V_old pushes the same secplus-v4 (with the field
          preserved). Gist content is unchanged.
  Step 5: V_new on Device A pulls. Gets same data back. No conflict.

  ✓ ADDITIVE SHAPE CHANGES are safe across the V_old/V_new transition
    AS LONG AS V_old's migrateStore preserves unknown fields. The
    current migrateStore does (line 80 in secplus-quiz.jsx).

  ⚠ Future-proofing: any change to migrateStore that DROPS unknown
    fields would break this safety. Comment the assumption in the
    code.

────────────
(c) Pure new keys (presets)
────────────

KEY: secplus-v4-presets

  Step 1: V_new on Device A writes the key.
  Step 2: V_new pushes. Gist's entries[] now has secplus-v4-presets.
  Step 3: V_old on Device B pulls. V_old's TRACKED_PREFIXES does
          include "secplus-" (it's the same engine), so isTracked()
          returns true for secplus-v4-presets. Merge passes the key
          through. applyMergedEntries writes it to V_old's
          localStorage.
  Step 4: V_old reads localStorage on next page load — its UI doesn't
          read secplus-v4-presets. Key sits unused in localStorage.
  Step 5: V_old pushes (after a normal write). Push payload is built
          from V_old's localStorage scan (scanTrackedKeys) — which
          INCLUDES secplus-v4-presets (V_old wrote it via
          applyMergedEntries in step 3). Gist content unchanged.

  ✓ Pure new keys with the EXISTING "secplus-" prefix are safe.
    V_old happily passes them through without understanding them.

────────────
(d) NEW PREFIX added to TRACKED_PREFIXES (cram-*)
────────────

THIS IS WHERE IT GETS DANGEROUS. Walk through carefully.

PREMISE: Sub-batch 4 adds "cram-" to TRACKED_PREFIXES on V_new's
sync-engine.js. V_old's sync-engine.js doesn't have it.

  Step 1: V_new on Device A writes cram-1.4.1-0 record.
  Step 2: V_new pushes. Gist's entries[] now has cram-1.4.1-0.
          Gist's wrapper schemaVersion still = 1 (no bump).
  Step 3: V_old on Device B pulls.
          - parsePayload accepts (schemaVersion match).
          - mergeEntries iterates over local + remote keys.
          - For key "cram-1.4.1-0": V_old's isTracked() checks
            "cram-" against V_old's TRACKED_PREFIXES = ["mc-", "scen-",
            "match-", "secplus-"]. NO MATCH.
          - Line 78: `if (!isTracked(k)) continue;` — the key is
            DROPPED from the merged set.
          - applyMergedEntries doesn't write it to V_old's
            localStorage.
  Step 4: V_old (after a normal user action that modifies a tracked
          key) builds its own push payload via buildLocalEntries
          → scanTrackedKeys.
          - V_old's localStorage doesn't contain cram-1.4.1-0
            (because step 3 dropped it).
          - V_old's push payload OMITS cram-* keys.
  Step 5: V_old PATCHes the gist with `{ files: { "secplus-sync.json":
          { content } } }`. The PATCH replaces the file content.
          Gist now has V_old's payload — WHICH DOES NOT INCLUDE
          cram-1.4.1-0. **DEVICE A'S CRAM PROGRESS IS WIPED FROM
          THE GIST.**
  Step 6: V_new on Device A pulls.
          - mergeEntries: local has cram-1.4.1-0; remote doesn't.
          - merge function: `if (!r) { out[k] = l; continue; }` —
            local survives.
          - applyMergedEntries writes the merged set to A's
            localStorage. cram-1.4.1-0 is preserved on Device A.
  Step 7: V_new pushes the merged set. Gist has cram-1.4.1-0 again.
  Step 8: V_old on Device B pulls again. SAME LOOP — drops the key,
          pushes without it, wipes the gist.

  STEADY-STATE: cram-* keys oscillate between gist and localStorage
  on Device A, getting wiped and re-pushed every time Device B is
  active. Device A never LOSES local data, but the gist is unstable.

  ⚠ DATA-LOSS SCENARIO:
    Step X: Device A's localStorage is cleared (browser cache wipe,
            new device, fresh login).
    Step X+1: Device A V_new pulls gist. Gist currently has no
              cram-* keys (last push was V_old's payload).
    Step X+2: Merge: local empty + remote no cram-* → no cram-* in
              merged set.
    Step X+3: applyMergedEntries writes merged set to A's
              localStorage. cram-* keys are NOT restored.
    Step X+4: User loses all cram SM-2 progress. UNRECOVERABLE
              without the user manually exporting before clear.

THIS IS WHY THE HYGIENE-FIRST DECOMPOSITION IS NECESSARY.

────────────
PROTOCOL: hygiene-first deployment
────────────

To safely add "cram-" to TRACKED_PREFIXES, we need to first ensure
ALL devices know to pass "cram-" through the merge filter. The
sequence:

  PHASE H (Hygiene): Deploy a sync-engine update that ONLY adds
                     "cram-" to TRACKED_PREFIXES (and adds
                     secplus-v4-exam-session to LOCAL_ONLY for the
                     pre-existing bug). NO cram-* keys are written
                     yet — the new prefix is just registered.

                     Validation: all 3 of Aiden's devices reload to
                     the new bundle. Sync indicator shows "Synced"
                     on each. (No data difference yet because no
                     cram-* keys exist.)

  PHASE F (Feature): After all 3 devices show V_hygiene loaded,
                     deploy the cram SM-2 feature. cram-* keys begin
                     to be written when user rates cards. All
                     devices' sync-engines now know to pass these
                     keys through merge.

  Verification of Phase H completion: Aiden manually checks the
  sync status pill on each of his 3 devices. The pill shows the
  bundle hash (or last sync time) — sufficient proxy for "this
  device has loaded the new bundle."

  Risk if Phase F deploys before Phase H is verified on all
  devices: see step 6 of (d) above. Device that's still on
  V_hygiene-minus (i.e., V_old) drops cram-* keys on merge and
  potentially wipes progress.

────────────
SECONDARY PROTOCOL: dual-write during the hygiene window?
────────────

Could V_new also write old-format data during the transition? For
cram-* this doesn't apply (no old format exists — cram is a new
feature). For RENAMED keys (which we don't have), dual-write would
be the standard approach.

For the exam-session LOCAL_ONLY change: V_new stops syncing
secplus-v4-exam-session. V_old continues to sync it. During the
transition, V_old's pulls receive V_new's exam-session writes (via
the existing TRACKED_PREFIXES match — exam-session is still
syncable from V_old's perspective). After all devices are on
V_new+LOCAL_ONLY, the key stops syncing. Net effect: a brief
asymmetric window where V_old might leak in-progress exam state to
V_new before V_new updates. Acceptable; exam-session leakage was
the pre-existing bug being fixed.

────────────────────────────────────────────────────────────────────────
5.5. Rollback
────────────────────────────────────────────────────────────────────────

Per-sub-batch rollback paths:

Sub-batch 0 (hygiene): revert deploy. cram-* prefix unregistered;
  exam-session resumes syncing. No data loss because no cram-*
  data exists yet.

Sub-batch 1 (UI scaffold): revert deploy. Old tab structure
  returns. No data touched.

Sub-batch 2 (Customise drawer): revert deploy. Drawer UI gone;
  modes return to hardcoded behavior. No data touched.

Sub-batch 3 (presets): revert deploy. Preset UI gone. presets data
  in localStorage orphans harmlessly.

Sub-batch 4 (Flashcards SM-2): MORE COMPLEX.
  If reverted AFTER users have rated cards:
    - cram-* keys exist in localStorage and gist.
    - Reverted code's TRACKED_PREFIXES no longer includes "cram-".
    - This RECREATES the data-loss scenario from 5.4(d) for the
      duration of the rollback.
  Mitigation: don't revert Sub-batch 4 lightly. If we must revert,
  also revert Sub-batch 0 simultaneously (both removing cram- from
  TRACKED_PREFIXES AND the cram-rating UI), so the next deploy is a
  clean re-do.
  Alternative mitigation: SOFT-revert — hide the rating UI but keep
  the data-layer changes. Users can't add new cram ratings; existing
  ratings stay intact and synced.

Sub-batch 5 (cleanup): revert deploy. Old code returns. No user
  impact.

User-facing recovery path: the existing Backup feature (Task 1.5a)
exports all of localStorage to a JSON file. If a user is concerned
about migration, they can backup before any sub-batch deploy and
restore if anything goes wrong. The backup file format includes the
version field, so a v2 backup restored on v2 code works fine.
