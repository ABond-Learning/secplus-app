1. EXECUTIVE SUMMARY
═══════════════════════════════════════════════════════════════════════════

Task 2 collapses 6 quiz sub-modes (Standard / New / Scenario / Spaced /
Weak / Matching) and the per-tab Cram into 5 mode-cards under a unified
Study tab: **Quiz**, **Flashcards**, **Review**, **Drill Wrong**, and
**Matching**. A Customise drawer with last-used persistence and a
visible filter summary expresses every study intent the old modes
captured plus new compositions the old modes couldn't express. Saved
presets persist named drawer configurations.

Top-level tabs become 3: Progress / Study / Exam. Sync stays in the
footer. Exam keeps its separate identity (timer + simulation framing
distinct from study sessions).

Migration risk centers on cross-device sync-engine prefix registration
for the new `cram-` SM-2 keys. This drives a hygiene-first
decomposition: Sub-batch 0 ships sync-engine prefix changes alone,
verifies across all 3 of Aiden's devices with a 24-hour wait, then
the linear feature track (1→5) proceeds.

Total estimated scope: 6 sub-batches across 4-5 sessions. Sub-batches
0, 3, and 5 are LOW risk; Sub-batches 1 and 2 are LOW-MEDIUM (1 is
pure UI; 2 has the buildPool refactor); Sub-batch 4 carries MEDIUM
risk because of sync behavior consequences (mitigated by Sub-batch 0
hygiene + 24-hour validation gate). Net LOC delta ~+700 to +1000;
deletions in Sub-batch 5 partially offset.

────────────────────────────────────────────────────────────────────────
3.3. The Customise drawer
────────────────────────────────────────────────────────────────────────

A side drawer (or expanded card section) on the Study tab, attached
to whichever mode is currently selected. Filter controls compose
with AND semantics. Mode-specific defaults pre-fill on first use of
each mode; subsequent use restores last-used filters (per Q-D).

Visibility requirement (Q-D): the drawer state — or a one-line
filter-summary chip — MUST be visible to the user before clicking
Start. Last-used persistence is unsafe if filters are invisible. The
implementation has two equivalent satisfying patterns:
  - Drawer always-open by default with filters visible inline.
  - Collapsed drawer with a one-line summary chip showing active
    filters (e.g., "D4 only · MC + Scenarios · prefer unseen · 25 Q").
The summary chip is the recommended pattern (less screen real
estate); drawer expands on click for editing.

Filter / scope controls (universal across modes):
  - Domain checkboxes (D1-D5), default ALL CHECKED, exam-weighted
    info captions.
  - Sub-objective filter (shown when exactly one domain is checked).
  - Specific-videos filter (searchable list, multi-select).
  - watchedOnly toggle (per Q-L, default ON across all modes;
    flipping off enables pre-watch skim — explicit opt-in).

Format / type controls:
  - questionTypes checkboxes: { mc, scen, match, cram }.
    Mode defaults:
      Quiz       → { mc: true,  scen: true,  match: false, cram: false }
      Flashcards → { mc: false, scen: false, match: false, cram: true  }
      Review     → { mc: true,  scen: true,  match: false, cram: false }
      Drill Wrong→ { mc: true,  scen: true,  match: false, cram: false }
      Matching   → { mc: false, scen: false, match: true,  cram: false }
                   (locked — cannot uncheck match in Matching mode)

Length / pacing controls:
  - Length slider:
      Quiz        → 5–50 (default 20)
      Flashcards  → 10–100 (default 25)
      Review      → "all due" (no slider; user can OPTIONALLY enable
                    a slider for capping the session — not in v1)
      Drill Wrong → "all matching" (no slider)
      Matching    → "all matching" (whole exercises don't subdivide)
  - activeRecall toggle (per Q-G, drawer-level — preset-saveable).
  - revealOptions toggle (drawer-level).

Quality / SM-2 filter controls (per-mode applicability):
  - preferUnseen toggle:
      Quiz default OFF; subsumes today's "New" mode when ON.
      Flashcards default OFF.
      Review: COMPOSES with includeUnseen — see Q-K table below.
      Drill Wrong default OFF (drilling targets seen-and-poor items).
      Matching default OFF.
  - belowAccuracy threshold slider (0.50–0.95):
      Drill Wrong default 0.70 (today's WEAK_SPOT_RATIO).
      Other modes default OFF (no threshold filter).
      Per-question scope only (per Q-F; video-level scope dropped).
  - dueOnly toggle (Review default ON; other modes default OFF).
  - includeUnseen toggle (Review-specific; per Q-K):

      Q-K state table:
      ┌─────────────┬─────────────────┬──────────────────────────────┐
      │ dueOnly     │ includeUnseen   │ Pool composition             │
      ├─────────────┼─────────────────┼──────────────────────────────┤
      │ true        │ false           │ Items with SM-2 records due  │
      │             │                 │   today only                 │
      │ true        │ true            │ Due items + unseen items     │
      │             │                 │   (today's "spaced" mode)    │
      │ false       │ true            │ Unseen items only            │
      │             │                 │   (equivalent to Quiz mode + │
      │             │                 │    preferUnseen=true)        │
      │ false       │ false           │ All matching items in scope  │
      │             │                 │   (effectively no SM-2       │
      │             │                 │    filter)                   │
      └─────────────┴─────────────────┴──────────────────────────────┘

  - showRatingPanel toggle (Flashcards-specific; per Q-B).
      Default ON. Toggle off for the no-pressure cram experience.
      Preset-saveable.

Pool preview: live count "Drawing N items from M videos" updates as
filters change. Empty pool disables Start button with a tooltip
explaining why.

5.2. Migration strategy per non-PRESERVED key
────────────────────────────────────────────────────────────────────────

KEY: secplus-v4-presets (NEW)
  When does migration run? On first read after Sub-batch 3 deploys.
  Read returns null → default to empty array `[]`. Idempotent.
  Reversible? Yes. Revert removes read code; key orphans harmlessly.
  Partial-completion concern? None — single-write atomicity.
  SM-2 risk? None — separate keyspace.

KEY: cram-{vid}-{cardIdx} (NEW)
  When does migration run? On first rating action by user. Until
  then, no cram-* keys exist anywhere.
  Reversible? Removing cram-* records resets cram SM-2 progress; no
  effect on MC/scenario/matching SM-2.
  Partial-completion concern? None — per-key atomic writes.
  SM-2 risk? Adds new SM-2 family; doesn't affect existing.
  TRACKED_PREFIXES change: requires "cram-" added to TRACKED_PREFIXES
  on the sync engine. Lands in Sub-batch 0 (hygiene). See §5.4.

LOCAL_ONLY change: adding `secplus-v4-exam-session` exact-match to
LOCAL_ONLY (per Q-H, folded into Sub-batch 0).
  When does the change take effect? On Sub-batch 0 deploy.
  Reversible? Yes. Removing the LOCAL_ONLY entry resumes syncing.
  Existing data impact? After deploy, exam-session no longer syncs;
  existing exam-session data on each device persists locally but
  stops cross-replicating. No corruption.
  SM-2 risk? None — exam-session isn't SM-2 data.
  Same risk profile and validation path as the cram- TRACKED_PREFIXES
  change → ships in same hygiene commit (Sub-batch 0).

The §5.3 code comment guards this invariant.

through merge and stores it locally. V_old's UI doesn't read it;
V_old's push includes it (scanTrackedKeys finds it in localStorage).
Round-trip safe.

────────────
(d) NEW PREFIX added to TRACKED_PREFIXES (cram-*)
────────────

This is the dangerous case the hygiene-first protocol mitigates.

WITHOUT hygiene-first deploy:
  Step 1: V_new on Device A writes cram-{vid}-{idx}. Pushes.
  Step 2: V_old on Device B pulls. V_old's TRACKED_PREFIXES doesn't
          include "cram-". On merge: isTracked("cram-...") = false.
          Key dropped from merged set. Not written to V_old's
          localStorage.
  Step 3: V_old (next user write) builds push payload from
          scanTrackedKeys. cram-* not in V_old's localStorage.
          PATCH replaces gist with V_old's payload. cram-* WIPED
          from gist.
  Step 4: V_new on Device A pulls. Local has cram-*; remote doesn't.
          Merge favors local. Local data persists ON DEVICE A.
  Step 5: V_new pushes the merged set. cram-* re-appears on gist.
  Step 6: Loop with V_old continues. cram-* oscillates.

  Data-loss tail: if V_new's local cram-* data is cleared (browser
  wipe / fresh device), V_new pulls a gist that's missing cram-*
  (because V_old just pushed without them). Cram progress is gone,
  unrecoverable without backup.

WITH hygiene-first deploy (Sub-batch 0 + 24-hour wait per Q-M):
  Step 1: Sub-batch 0 ships. Adds "cram-" to TRACKED_PREFIXES on
          the sync-engine. ALSO adds secplus-v4-exam-session to
          LOCAL_ONLY (per Q-H).
  Step 2: Deploy. All 3 of Aiden's devices reload bundle within the
          24-hour wait (manual reload per Q-M).
  Step 3: ALL devices' TRACKED_PREFIXES now include "cram-". The
          merge filter passes cram-* keys through cleanly.
  Step 4: Sub-batch 4 ships (cram SM-2 feature). cram-* keys are
          written; flow through merge cleanly on all devices.

────────────
PROTOCOL SUMMARY (per Q-M and Q-O)
────────────

  Sub-batch 0 (Hygiene): ships standalone. NO feature work.
    - Add "cram-" to TRACKED_PREFIXES.
    - Add { kind: "exact", value: "secplus-v4-exam-session" } to
      LOCAL_ONLY.
  Verification: Aiden manually reloads each of his 3 devices.
    Confirms via the sync status pill (or DevTools) that the new
    bundle is loaded on each.
  Wait: 24 hours minimum between Sub-batch 0 ship and Sub-batch 4
    ship. Belt-and-braces — accounts for stale tabs, devices in
    standby, browser caches that haven't refreshed.
  Sub-batch 4 ships only after 24-hour wait elapses AND manual
    device verification confirms.

  Linear feature track (1 → 2 → 3 → 5) can run in parallel with the
  Sub-batch 0 verification window — these don't depend on the cram-
  prefix being everywhere.

────────────────────────────────────────────────────────────────────────
5.5. Rollback
────────────────────────────────────────────────────────────────────────

Sub-batch 0: revert deploy. cram- prefix unregistered; exam-session
  resumes syncing. Safe because no cram-* data exists yet.

Sub-batch 1 (UI scaffold): revert deploy. Old tab structure
  returns. No data touched.

Sub-batch 2 (buildPool + Customise drawer): revert deploy. Drawer
  UI gone; modes return to hardcoded behavior. No data touched.

Sub-batch 3 (presets): revert deploy. Preset UI gone. presets data
  in localStorage orphans harmlessly.

Sub-batch 4 (Flashcards SM-2): MORE COMPLEX.
  If reverted AFTER users have rated cards:
    - cram-* keys exist in localStorage and gist.
    - Reverted code's Flashcards UI no longer renders rating panel.
    - cram-* keys still flow through sync (TRACKED_PREFIXES change
      from Sub-batch 0 is still in place).
  Mitigation: SOFT-revert preferred. Hide the rating UI but keep
    the sync-engine prefix. Data continues to round-trip safely.
    HARD-revert (rolling back Sub-batch 0 too) re-creates the data-
    loss scenario from §5.4(d) during the next deploy.

Sub-batch 5 (cleanup): revert deploy. Old code returns. No user
  impact.

User-facing recovery path: existing Backup feature (Task 1.5a)
exports all of localStorage to a JSON file. Users can backup before
any sub-batch deploy.
